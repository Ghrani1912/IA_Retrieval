# Requirements Document

## Introduction

The Historical Intelligence & RAG Platform is an AI-powered research system built on top of the Internet Archive (IA). It enables users to search, retrieve, analyze, and reason over historical documents, books, research papers, government publications, and archived websites spanning decades. The platform combines BM25 full-text search, dense vector retrieval, Reciprocal Rank Fusion (RRF), and a cross-encoder reranker to surface the most relevant historical evidence. Every AI-generated answer is grounded in cited sources labeled DIRECTLY VERIFIED, INFERRED, or UNKNOWN, so users can trust and trace every claim.

The MVP targets public-domain books, research papers, government documents, and a single website domain module backed by the Wayback CDX API. Subsequent phases add newspaper/magazine collections, multi-domain website comparison, multimodal support, and a knowledge graph.

## Glossary

- **Platform**: The Historical Intelligence & RAG Platform — the system described in this document.
- **IA**: Internet Archive — the external archive service at archive.org.
- **IA Advanced Search API**: The Internet Archive's publicly available search endpoint for discovering item identifiers and metadata.
- **Metadata API**: The Internet Archive's per-item API that returns structured metadata and file lists.
- **CDX API**: The Wayback Machine's CDX Server API for querying snapshot history of a URL or domain.
- **Memento API**: The Wayback Machine's Memento API for fetching raw HTML of a specific archived snapshot.
- **Ingestion Pipeline**: The backend subsystem that discovers, fetches, cleans, chunks, embeds, and indexes source documents.
- **Chunk**: A text segment of approximately 400–600 tokens produced from a source document, used as the atomic unit of retrieval.
- **Embedding**: A dense vector representation of a Chunk generated by the BGE-M3 embedding model.
- **BM25 Index**: The OpenSearch-based sparse full-text index used for keyword retrieval.
- **Vector DB**: The Qdrant-based vector store holding Chunk Embeddings and metadata payloads.
- **RRF**: Reciprocal Rank Fusion — the score-combination method that merges ranked lists from BM25 and vector search.
- **Reranker**: The BGE cross-encoder model that re-scores the top RRF candidates and returns the final top 8–12 Chunks.
- **Query Engine**: The backend subsystem that executes retrieval, fusion, reranking, and LLM synthesis for a user query.
- **LLM**: A large language model used for query understanding and answer synthesis.
- **Answer**: A synthesized response generated by the LLM from the top-ranked Chunks for a given user query.
- **Citation**: A link from a claim in an Answer to the Chunk that supports it, tagged with a confidence label.
- **Confidence Label**: One of `directly_verified`, `inferred`, or `unknown` — assigned to each Citation.
- **Source**: A document, book, paper, government publication, or archived website stored in the Platform's database.
- **Source Type**: A classification of a Source: `public_domain_book`, `in_copyright_book`, `research_paper`, `government_document`, `magazine`, `newspaper`, `archived_website`, `image`, or `audio_video`.
- **Snapshot**: A single archived capture of a URL at a specific timestamp, managed via CDX/Memento APIs.
- **Temporal Filter**: A filter on retrieval that restricts results to sources published or captured within a specified date range.
- **Capture Timestamp**: The date and time a website Snapshot was archived by the Wayback Machine — distinct from the original publication or launch date.
- **Object Storage**: An S3-compatible store that caches raw source files to reduce dependence on live IA API availability.
- **PostgreSQL DB**: The relational database storing Source metadata, Snapshot metadata, user data, and saved research collections.
- **Research Collection**: A user-curated set of saved Sources, Answers, and Citations organized around a research topic.
- **OCR**: Optical Character Recognition — the pre-computed text extracted from scanned documents by IA (`_djvu.txt`, `_hocr.html`).
- **Source Explorer**: The UI panel that lets users browse, filter, and inspect Sources and Snapshots.
- **Timeline View**: The UI component that renders source density and Snapshot history along a time axis.
- **Research Chat**: The UI interface through which users submit queries and receive cited Answers.
- **Recall@K**: The fraction of relevant documents found in the top K retrieval results.
- **nDCG@K**: Normalized Discounted Cumulative Gain at rank K — a standard ranking quality metric.
- **MRR**: Mean Reciprocal Rank — the average of the reciprocal rank of the first relevant result.
- **Faithfulness Score**: A measure of whether every claim in an Answer traces to a cited Chunk that supports it.

## Requirements

### Requirement 1: Source Ingestion — Public-Domain Books

**User Story:** As a researcher, I want the Platform to ingest and index public-domain books from the Internet Archive, so that I can retrieve and cite historical book content in my research queries.

#### Acceptance Criteria

1. WHEN the Ingestion Pipeline runs for the `public_domain_book` source type, THE Ingestion_Pipeline SHALL discover item identifiers via the IA Advanced Search API using collection and date filters that restrict results to items published before 1928 (US) or explicitly marked as public domain.
2. WHEN an item identifier is discovered, THE Ingestion_Pipeline SHALL fetch structured metadata from the Metadata API including title, author, publisher, publication date, language, subjects, collection name, and IA URL, and store this in the PostgreSQL DB `sources` table.
3. WHEN a public-domain book item has an associated `_djvu.txt` or `_hocr.html` file, THE Ingestion_Pipeline SHALL fetch the OCR text from that file and cache the raw file in Object Storage.
4. IF a public-domain book item has no `_djvu.txt` or `_hocr.html` file, THEN THE Ingestion_Pipeline SHALL mark the item as `text_unavailable` in the PostgreSQL DB and skip chunking for that item.
5. WHEN OCR text is fetched, THE Ingestion_Pipeline SHALL apply text cleaning that includes dehyphenation, OCR artifact removal, and preservation of page and section markers.
6. WHEN cleaned text is available, THE Ingestion_Pipeline SHALL split the text into Chunks of 400–600 tokens each, retaining page number and section anchor metadata per Chunk.
7. WHEN Chunks are produced, THE Ingestion_Pipeline SHALL generate an Embedding for each Chunk using the BGE-M3 model and store the Embedding in the Vector DB with a metadata payload containing the source identifier, page number, and capture timestamp (null for books).
8. WHEN Chunks are produced, THE Ingestion_Pipeline SHALL index each Chunk's text and metadata in the BM25 Index.
9. THE Ingestion_Pipeline SHALL store a link to the original scan image alongside each Chunk's OCR text in the PostgreSQL DB, so that the source scan is accessible as evidence without the Platform silently replacing it with cleaned text.
10. WHEN an ingestion run completes for a batch of items, THE Ingestion_Pipeline SHALL log the count of items discovered, successfully processed, skipped (text unavailable), and failed with error details.

### Requirement 2: Source Ingestion — Research Papers and Government Documents

**User Story:** As a researcher, I want the Platform to ingest and index research papers and government documents from the Internet Archive, so that I can retrieve openly accessible academic and policy content.

#### Acceptance Criteria

1. WHEN the Ingestion Pipeline runs for the `research_paper` or `government_document` source type, THE Ingestion_Pipeline SHALL discover items via the IA Advanced Search API filtered by the appropriate collection identifiers for open-access academic and government document collections.
2. WHEN a research paper or government document item provides full text via `_djvu.txt`, `_hocr.html`, or a downloadable PDF, THE Ingestion_Pipeline SHALL fetch the full text and follow the same cleaning, chunking, embedding, and indexing steps defined in Requirement 1 Criteria 5–9.
3. WHEN a research paper or government document provides only metadata without accessible full text, THE Ingestion_Pipeline SHALL store the item metadata and mark the item as `metadata_only` in the PostgreSQL DB.
4. THE Ingestion_Pipeline SHALL support independent ingestion adapter configuration per source type, so that adding or modifying one source type's ingestion logic does not require changes to adapters for other source types.

### Requirement 3: Source Ingestion — Archived Websites (CDX/Wayback Module)

**User Story:** As a researcher, I want the Platform to ingest snapshot history for a specified website domain using the Wayback CDX API, so that I can analyze how a website's content changed over time.

#### Acceptance Criteria

1. WHEN a user or administrator provides a domain for ingestion, THE Ingestion_Pipeline SHALL query the CDX API to retrieve the complete snapshot list for that domain, including snapshot URL, timestamp, HTTP status code, and content digest.
2. WHEN CDX API results are retrieved for a domain, THE Ingestion_Pipeline SHALL store all snapshot records in the PostgreSQL DB `website_snapshots` table, keyed by domain, URL, and timestamp.
3. AFTER storing CDX results, THE Ingestion_Pipeline SHALL compute and store per-domain statistics in the PostgreSQL DB, including earliest snapshot timestamp, latest snapshot timestamp, total snapshot count, snapshot count per year, and identified gap periods exceeding 90 days.
4. THE Ingestion_Pipeline SHALL NOT query the CDX API live per user request; THE Ingestion_Pipeline SHALL serve all snapshot list queries from the PostgreSQL DB cache.
5. WHEN the CDX API returns a rate-limit response (HTTP 429), THE Ingestion_Pipeline SHALL apply exponential backoff starting at 2 seconds and retry up to 5 times before marking the batch as failed.
6. WHEN a user or administrator requests on-demand fetching of a specific Snapshot, THE Ingestion_Pipeline SHALL retrieve the raw HTML for that Snapshot via the Memento API, extract text from the HTML, and follow the same chunking, embedding, and indexing steps defined in Requirement 1 Criteria 6–8.
7. WHEN storing Chunks derived from an archived website Snapshot, THE Ingestion_Pipeline SHALL tag each Chunk with the Capture Timestamp of the Snapshot and SHALL NOT infer or substitute the original website's launch or publication date as the Capture Timestamp.
8. WHEN a Snapshot's raw HTML is fetched via the Memento API, THE Ingestion_Pipeline SHALL cache the raw HTML in Object Storage to prevent re-fetching the same Snapshot from the Wayback Machine.

### Requirement 4: In-Copyright Book Handling

**User Story:** As a researcher, I want the Platform to clearly indicate when a book is in copyright and unavailable for full-text retrieval, so that I understand the scope of what can be cited.

#### Acceptance Criteria

1. WHEN the Ingestion Pipeline discovers a book item that was published in 1928 or later and is not explicitly marked as public domain, THE Ingestion_Pipeline SHALL store only the item's metadata and SHALL mark the item's `access_level` as `metadata_only` in the PostgreSQL DB.
2. WHEN the Query Engine retrieves results that include an in-copyright book, THE Query_Engine SHALL include the book's metadata in the response and SHALL indicate to the user that full text is not available for that item.
3. THE Platform SHALL NOT expose or cache full OCR text for items marked `metadata_only` due to copyright restrictions.

### Requirement 5: Hybrid Retrieval — BM25 and Vector Search

**User Story:** As a researcher, I want the Platform to use both keyword and semantic search when processing my query, so that I receive the most relevant historical evidence regardless of exact wording.

#### Acceptance Criteria

1. WHEN the Query Engine processes a user query, THE Query_Engine SHALL execute a BM25 search against the BM25 Index and return the top 50 Chunks ranked by BM25 score.
2. WHEN the Query Engine processes a user query, THE Query_Engine SHALL generate a query Embedding using the BGE-M3 model and execute a vector similarity search against the Vector DB and return the top 50 Chunks ranked by cosine similarity score.
3. WHEN a Temporal Filter is specified in the query, THE Query_Engine SHALL apply the date range filter to both BM25 and vector search results, restricting Chunks to those whose associated source publication date or Capture Timestamp falls within the specified range.
4. WHEN a source type filter is specified in the query, THE Query_Engine SHALL restrict BM25 and vector search results to Chunks whose associated Source has the specified Source Type.
5. WHEN both BM25 and vector search results are available, THE Query_Engine SHALL merge the ranked lists using Reciprocal Rank Fusion to produce a combined ranked list.
6. WHEN the RRF combined list is produced, THE Query_Engine SHALL pass the top candidates to the Reranker, which SHALL use the BGE cross-encoder model to re-score candidates and return the top 8–12 Chunks as the final retrieved set.
7. THE Query_Engine SHALL execute BM25 search and vector search in parallel to minimize total retrieval latency.

### Requirement 6: Query Understanding

**User Story:** As a researcher, I want the Platform to interpret my natural-language query and extract structured parameters, so that temporal filters and source preferences are applied automatically when evident from my question.

#### Acceptance Criteria

1. WHEN a user submits a query, THE Query_Engine SHALL call the LLM to extract the research topic, an optional date range, and an optional source type hint from the query text.
2. WHEN the LLM extracts a date range from the query, THE Query_Engine SHALL use the extracted date range as the Temporal Filter for retrieval.
3. WHEN the LLM cannot determine a date range from the query, THE Query_Engine SHALL apply no Temporal Filter and retrieve across all available time periods.
4. IF the LLM query understanding call fails or times out, THEN THE Query_Engine SHALL proceed with the raw user query text and no automated filters, and SHALL log the failure.

---

### Requirement 7: Answer Synthesis and Citation

**User Story:** As a researcher, I want every AI-generated answer to be grounded in cited source Chunks with a confidence label, so that I can verify each claim and trust the information provided.

#### Acceptance Criteria

1. WHEN the Query Engine has the final top 8–12 Chunks from the Reranker, THE Query_Engine SHALL call the LLM to synthesize an Answer using only those Chunks as the evidence context.
2. WHEN the LLM synthesizes an Answer, THE Query_Engine SHALL require the LLM to associate each factual claim in the Answer with a specific Chunk identifier and a Confidence Label of `directly_verified`, `inferred`, or `unknown`.
3. THE Query_Engine SHALL define `directly_verified` as: the Chunk contains verbatim or near-verbatim text that directly supports the claim; `inferred` as: the claim is a reasonable conclusion drawn from one or more Chunks but is not stated explicitly; `unknown` as: the claim cannot be traced to any retrieved Chunk.
4. WHEN an Answer is generated, THE Query_Engine SHALL store each Citation in the PostgreSQL DB `evidence_citations` table with the answer identifier, chunk identifier, and Confidence Label.
5. WHEN an Answer is returned to the user, THE Answer SHALL include the full text of the response and a structured list of Citations, each containing the Chunk text excerpt, the Source title and author, the Source publication date or Capture Timestamp, the IA URL, and the Confidence Label.
6. IF the LLM synthesis call fails, THEN THE Query_Engine SHALL return an error response to the user without a partial Answer and SHALL log the failure with the query identifier and error details.

### Requirement 8: Capture Timestamp vs. Publication Date Disambiguation

**User Story:** As a researcher, I want the Platform to clearly distinguish between when content was published and when it was archived, so that I am not misled about the original date of a source.

#### Acceptance Criteria

1. THE PostgreSQL DB `chunks` table SHALL maintain separate fields for `source_pub_date` (the original publication date of the source document) and `capture_timestamp` (the Wayback Machine capture date), and SHALL allow `capture_timestamp` to be NULL for non-website sources.
2. WHEN the LLM synthesizes an Answer that references an archived website Snapshot, THE Query_Engine SHALL instruct the LLM to use the Capture Timestamp in any date reference for that Snapshot and SHALL NOT permit the LLM prompt to substitute or conflate the Capture Timestamp with an inferred original launch or publication date.
3. WHEN the Source Explorer or Timeline View displays a website Snapshot, THE Platform SHALL label the date as "Archived: [capture date]" and SHALL NOT display it as "Published: [date]" or any other label that implies the capture date is the original publication date.

### Requirement 9: Object Storage Cache and IA API Resilience

**User Story:** As a platform operator, I want all fetched source files to be cached in object storage, so that temporary Internet Archive outages do not break the application for content already ingested.

#### Acceptance Criteria

1. WHEN the Ingestion Pipeline successfully fetches a raw source file (OCR text file, HTML Snapshot, PDF) from IA, THE Ingestion_Pipeline SHALL store a copy of that file in Object Storage, keyed by the IA item identifier and file name.
2. WHEN the Ingestion Pipeline requires a raw source file for chunking or re-processing, THE Ingestion_Pipeline SHALL check Object Storage first and SHALL only fetch from IA if the file is not present in Object Storage.
3. WHEN the IA API returns an error or is unreachable, THE Ingestion_Pipeline SHALL serve previously cached files from Object Storage and SHALL log the IA API failure with timestamp and endpoint details.
4. WHEN the IA API returns an error or is unreachable, THE Query_Engine SHALL continue to serve retrieval and Answer generation using the already-indexed content and SHALL NOT degrade to returning empty results for indexed sources.

### Requirement 10: Retrieval Evaluation Framework

**User Story:** As a platform developer, I want a structured evaluation framework that benchmarks the five retrieval configurations against a hand-labeled query set, so that I can measure and improve retrieval quality before launch.

#### Acceptance Criteria

1. THE Platform SHALL provide an evaluation module that accepts a hand-labeled query set of 30–50 queries, where each query has an associated list of ground-truth relevant Chunk or Source identifiers.
2. WHEN the evaluation module runs, THE Evaluation_Module SHALL execute each query against each of the five retrieval configurations: (1) vector-only, (2) BM25-only, (3) vector + BM25 simple merge, (4) vector + BM25 + RRF, and (5) vector + BM25 + RRF + Reranker.
3. WHEN the evaluation module runs, THE Evaluation_Module SHALL compute Recall@10, Precision@10, MRR, and nDCG@10 for each configuration and query.
4. WHEN the evaluation module runs, THE Evaluation_Module SHALL compute a faithfulness score per query by verifying that each claim in the synthesized Answer is traceable to a cited Chunk, using the LLM as a judge.
5. WHEN the evaluation module runs, THE Evaluation_Module SHALL compute a citation correctness score per query by verifying that each cited Chunk actually contains text that supports the associated claim.
6. WHEN evaluation completes, THE Evaluation_Module SHALL output a results report containing per-configuration metric summaries, per-query breakdowns, and a ranked comparison of the five configurations by nDCG@10.
7. THE Evaluation_Module SHALL be executable as a standalone CLI command, independent of the live Query Engine, so that evaluation can be run offline without user traffic.

### Requirement 11: Research Chat UI

**User Story:** As a researcher, I want a conversational chat interface where I can ask historical research questions and receive cited, evidence-grounded answers, so that I can efficiently conduct research without manually browsing document archives.

#### Acceptance Criteria

1. THE Research_Chat SHALL provide a text input field through which users can submit natural-language queries.
2. WHEN a user submits a query, THE Research_Chat SHALL display a loading indicator while the Query Engine processes the request.
3. WHEN an Answer is returned, THE Research_Chat SHALL render the Answer text with inline citation markers linked to the corresponding Citation details.
4. WHEN a user activates a citation marker, THE Research_Chat SHALL display the cited Chunk text excerpt, Source title, author, publication date or Capture Timestamp, IA URL, and Confidence Label.
5. WHEN an Answer includes Citations with `unknown` Confidence Labels, THE Research_Chat SHALL visually distinguish those Citations from `directly_verified` and `inferred` Citations.
6. THE Research_Chat SHALL allow users to apply Temporal Filters and Source Type filters directly in the chat interface before submitting a query.
7. THE Research_Chat SHALL allow users to save an Answer and its Citations to a Research Collection.

---

### Requirement 12: Source Explorer UI

**User Story:** As a researcher, I want a browsable explorer for all indexed sources, so that I can discover and inspect historical materials beyond what surfaces in a single chat query.

#### Acceptance Criteria

1. THE Source_Explorer SHALL display a filterable list of all indexed Sources, supporting filters on Source Type, publication date range, language, collection, and subject.
2. WHEN a user selects a Source, THE Source_Explorer SHALL display the Source's title, author, publisher, publication date, language, subjects, collection, IA URL, and access level (`full_text` or `metadata_only`).
3. WHEN a Source is a `public_domain_book`, `research_paper`, or `government_document` with full text available, THE Source_Explorer SHALL provide a link to the original scan or file on the Internet Archive.
4. WHEN a Source is an archived website, THE Source_Explorer SHALL display the computed per-domain statistics including earliest and latest snapshot timestamps, total snapshot count, and snapshot count per year.
5. THE Source_Explorer SHALL display the access level (`metadata_only`) for in-copyright books and SHALL NOT present a mechanism to access or download full text for those items.

---

### Requirement 13: Timeline View UI

**User Story:** As a researcher, I want a timeline visualization showing when sources were published and when websites were archived, so that I can understand the temporal distribution of evidence and identify historical gaps.

#### Acceptance Criteria

1. THE Timeline_View SHALL display a time-axis visualization showing the density of indexed Sources by publication year across the full date range of the corpus.
2. WHEN a user applies a Temporal Filter in the Research Chat or Source Explorer, THE Timeline_View SHALL update to highlight the filtered date range and the Sources within it.
3. WHEN a domain has been ingested for website archiving, THE Timeline_View SHALL display the Snapshot history for that domain as a separate series, showing snapshot frequency by year and highlighting gap periods where no snapshots exist.
4. WHEN a user selects a year or range on the Timeline_View, THE Timeline_View SHALL filter the Source Explorer to show only Sources published within the selected range.
5. THE Timeline_View SHALL visually distinguish the Capture Timestamp series for archived websites from the publication date series for documents, using distinct labels and visual styles.

---

### Requirement 14: Research Collections

**User Story:** As a researcher, I want to save and organize sources and answers into named collections, so that I can return to and build on previous research sessions.

#### Acceptance Criteria

1. THE Platform SHALL allow authenticated users to create, name, and delete Research Collections.
2. WHEN a user saves a Source to a Research Collection, THE Platform SHALL store the Source identifier and the user's annotation in the PostgreSQL DB linked to the user's collection.
3. WHEN a user saves an Answer to a Research Collection, THE Platform SHALL store the Answer text, all associated Citations, and the original query in the PostgreSQL DB linked to the user's collection.
4. WHEN a user opens a Research Collection, THE Platform SHALL display all saved Sources and Answers in that collection, with Citations intact and navigable.
5. THE Platform SHALL allow authenticated users to export a Research Collection as a structured JSON file containing all saved Sources, Answers, Citations, and annotations.

### Requirement 15: Rate Limit and API Compliance

**User Story:** As a platform operator, I want the Platform to respect the Internet Archive's API rate limits and usage policies, so that the Platform is not blocked and remains operational.

#### Acceptance Criteria

1. WHEN making requests to the CDX API, THE Ingestion_Pipeline SHALL enforce a maximum sustained request rate of 60 requests per minute per IP address.
2. WHEN making bulk discovery requests to the IA Advanced Search API, THE Ingestion_Pipeline SHALL introduce a minimum delay of 1 second between consecutive requests and SHALL use the IA API's pagination parameters rather than repeatedly querying from offset 0.
3. THE Ingestion_Pipeline SHALL NOT fetch live CDX results per user query; all CDX data accessed at query time SHALL be served from the PostgreSQL DB cache.
4. WHEN the IA API returns an HTTP 429 response, THE Ingestion_Pipeline SHALL apply exponential backoff starting at 2 seconds with a jitter of up to 1 second and retry up to 5 times before logging the request as failed.
5. THE Ingestion_Pipeline SHALL record the timestamp, endpoint, and HTTP status code of every IA API request in the PostgreSQL DB for auditing and rate-limit monitoring purposes.

---

### Requirement 16: System Observability and Logging

**User Story:** As a platform operator, I want structured logs and error records for all ingestion, retrieval, and API operations, so that I can diagnose failures and monitor system health.

#### Acceptance Criteria

1. THE Platform SHALL emit structured JSON log entries for every ingestion job, including job start time, source type, item count discovered, items successfully indexed, items skipped, items failed, and job end time.
2. WHEN any IA API call fails with a non-retriable error, THE Platform SHALL log the endpoint URL, HTTP status code, error message, and a unique request trace identifier.
3. WHEN the Query Engine processes a query, THE Platform SHALL log the query identifier, query text (truncated to 500 characters), number of Chunks retrieved from each search path, reranker output count, LLM call latency, and total query latency.
4. WHEN an Answer is generated with one or more Citations labeled `unknown`, THE Platform SHALL log the query identifier and the count of `unknown`-labeled Citations for monitoring answer quality.
5. THE Platform SHALL expose a health check endpoint that returns the operational status of the PostgreSQL DB, BM25 Index, Vector DB, and Object Storage connections, returning HTTP 200 when all services are reachable and HTTP 503 when any service is unreachable.
